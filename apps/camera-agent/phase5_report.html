8. Hardware-availability note (honest observation)

Today the camera dropped off the USB bus twice; once while the Phase 5 agent was already running: fresh-SDK count was 0 while the agent's in-process cached enumeration kept the stale entry, so /preview still returned the 409 busy path (the conservative fallback — _device_gone() matched the serial against the fresh manager's own refreshed list, which still carried the stale entry) rather than 503. After the user replugged, the agent self-recovered with no restart (status → connected:true + resolution, preview 200), and all Phase 5 flows above ran on that recovered session.

Consequence: the unplugged-while-agent-running case can still surface as busy-type in some drop sequences (when the stale entry persists in the very manager the fresh check also updates). The five new tests prove the mapping is correct when the fresh manager is authoritative (verified probe: count=0 unplugged / count=1 replugged). The residual gap is SDK-internal cache behavior during PnP removal — documented as a known limitation, not papered over with fragile heuristics. Every path remains typed, recoverable, and crash-free.

10. Known limitations

  1. Unplug-vs-busy during live PnP removal (§8): some failure sequences still surface as 409 busy instead of 503 disconnected. Typed + recoverable either way; bounded by mvIMPACT's in-process device-list caching. Future work: reopen the DeviceManager process-wide on any open failure (costs the multi-second re-open), or SDK hot-plug callbacks if exposed.
  2. "Analysis started…" is transient on fast runs — the result may already be rendered between DOM polls (observed live). Wording itself is correct.
  3. Panel error text can persist until the next action (pre-existing cosmetic, Phase 3 note).
  4. No exposure/gain/focus controls, no WebSocket/MJPEG streaming, no pixel enhancement — all excluded by scope and NOT added.
  5. Metallurgical ground truth: still none; accuracy/confidence remain engine self-check values, not metallographic verdicts.
